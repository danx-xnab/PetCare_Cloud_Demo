# PetCare Cloud — 基于 LLM 的对话式多宠物管理系统
## 云计算课程项目报告

---

## 一、项目背景与现实意义

### 1.1 背景

近年来，中国宠物行业持续扩张，2023 年城镇宠物（犬猫）数量超过 1.4 亿只，宠物消费市场规模突破 2700 亿元。养宠群体呈现两个显著痛点：

**痛点一：养宠前缺乏科学决策依据。** 许多用户因对不同宠物的空间需求、陪伴时间、经济成本认知不足，导致弃养率居高不下。

**痛点二：养宠后记录管理繁琐。** 多宠物家庭需要追踪每只宠物的喂食、疫苗、驱虫、用药、体重等信息，传统表单式 App 操作门槛高，用户坚持使用率低。

### 1.2 项目定位

PetCare Cloud 不是简单的聊天机器人，也不是普通的宠物记录 App，而是：

> **养宠前推荐 + 养宠后管理 + 对话式记录 + 自动提醒**

的完整闭环系统。其核心创新在于：**用户像发微信一样输入一句话，系统通过 LLM 自动理解并整理成结构化记录**。

### 1.3 现实意义与价值

| 维度 | 传统宠物 App | PetCare Cloud |
|------|-------------|---------------|
| 记录方式 | 手动填写多个表单字段 | 自然语言一句话，LLM 自动解析 |
| 提醒生成 | 手动创建日历事件 | 从对话中自动识别并生成提醒 |
| 多宠物管理 | 切换宠物档案，逐条查看 | 统一聊天流，按宠物名自动归档 |
| 养宠决策 | 查阅文章自行判断 | AI 个性化问卷推荐 |
| 健康分析 | 无 | LLM 生成近期健康摘要和护理建议 |

## 二、详细需求描述

### 2.1 功能需求

#### F1 — 用户登录
- 账号密码登录；会话持久化（localStorage），刷新页面不丢失登录态

#### F2 — 宠物档案管理（CRUD）
- 添加宠物：名称、种类、品种、生日、体重、备注
- 编辑宠物信息；删除宠物（级联删除相关日志和提醒）
- 上传宠物头像（Base64 传输，服务端存储）

#### F3 — 对话式记录（核心功能）
- 用户在聊天框输入自然语言，如：
  - `"小橘今天晚上吐了一次，没怎么吃饭，明天早上提醒我观察"`
  - `"豆豆今晚八点吃了药，明晚还要再吃一次"`
  - `"小橘今天打了狂犬疫苗，一年后再打"`
- 系统自动识别：宠物名、记录类型、严重程度、症状列表、提醒需求
- 自动写入健康日志，并在需要时生成提醒

#### F4 — 健康日志
- 按宠物、按记录类型（健康/用药/饮食/疫苗/驱虫/日常）筛选
- 显示严重级别（低/中/高）及症状标签
- 一键生成近期健康摘要（LLM 优先，规则兜底）

#### F5 — 提醒管理
- 自动提醒：从聊天记录中自动生成
- 手动提醒：表单创建，指定宠物和时间
- 完成/删除操作；逾期提醒红色标注

#### F6 — 养宠选择推荐
- 6 维度问卷（居住空间、陪伴时间、预算、经验、过敏、偏好）
- LLM 配置后生成个性化解释；未配置时使用规则引擎推荐

#### F7 — LLM 动态配置
- 前端弹窗输入 API Key / Base URL / 模型名
- 实时保存到服务端内存，后续所有 LLM 调用立即生效
- 状态指示（侧边栏绿点/红点）

#### F8 — 语音输入
- 浏览器 Web Speech API（Chrome/Edge 支持）
- 点击麦克风按钮，语音转文字填入聊天框

#### F9 — 云架构展示
- 展示各云服务节点状态（ECS、数据库、对象存储、LLM、消息队列）
- 架构流程图

### 2.2 非功能需求

| 需求 | 指标 |
|------|------|
| 零依赖部署 | 后端仅用 Python 标准库，可在裸 ECS 直接运行 |
| LLM 可选 | 无 API Key 时规则引擎全量兜底，功能不降级 |
| 响应式 | 适配 PC、平板、手机（CSS Grid 自适应） |
| 数据安全 | 文件路径访问权限检查；HTML 输出全部转义防 XSS |
| 可扩展性 | SQLite → RDS 零代码改动；同步处理 → RocketMQ 异步就绪 |

## 三、解决方案设计

### 3.1 概要设计

```
浏览器 SPA（Vanilla JS）
    │  HTTP JSON API
    ▼
Python 标准库 HTTP Server（单文件 server.py）
    ├── 路由分发（GET / POST / PUT / DELETE）
    ├── 业务逻辑层
    │       ├── 宠物 CRUD
    │       ├── 聊天解析（LLM → 规则兜底）
    │       ├── 健康日志 & 提醒
    │       └── 推荐引擎（LLM → 规则兜底）
    └── 数据层（SQLite via sqlite3 标准库）
```

### 3.2 详细设计

#### 3.2.1 后端架构

**技术选型：** 纯 Python 标准库（无 FastAPI、无 Django）。选型依据：
- 可在裸 ECS / Docker 直接运行，无需 pip install
- 教学演示场景下结构更透明
- `ThreadingHTTPServer` 支持并发请求

**数据库模型（5 张表）：**

```
users          id, username, password, created_at
pets           id, user_id, name, species, breed, birthday, weight, avatar_url, notes
chat_messages  id, user_id, pet_id, raw_content, input_type, parsed_result(JSON), created_at
health_logs    id, pet_id, date, record_type, symptoms(JSON), summary, severity, source_message_id
reminders      id, pet_id, title, reminder_time, repeat_rule, status, source_message_id
```

**API 端点（RESTful）：**

| 方法 | 路径 | 功能 |
|------|------|------|
| GET | `/api/state` | 一次性获取完整应用状态 |
| POST | `/api/auth/login` | 登录 |
| POST/PUT/DELETE | `/api/pets[/{id}]` | 宠物 CRUD |
| POST | `/api/pets/{id}/summarize` | 健康摘要（LLM） |
| POST | `/api/chat` | 聊天式记录（LLM 解析） |
| POST/DELETE | `/api/reminders[/{id}]` | 提醒管理 |
| POST | `/api/reminders/{id}/complete` | 完成提醒 |
| POST | `/api/recommend` | 养宠推荐（LLM） |
| POST/GET | `/api/llm/config` `/api/llm/status` | LLM 动态配置 |
| POST | `/api/upload` | 头像上传 |

#### 3.2.2 LLM 集成设计（核心）

采用 **"LLM 优先 + 规则兜底"** 双层架构：

```
用户输入文本
    │
    ├─ API Key 已配置？
    │       │ YES → call_llm() → OpenAI 兼容接口
    │       │           ├── 解析成功 → normalize_parse() → 返回结构化数据
    │       │           └── 失败（超时/格式错误）→ 降级
    │       │
    │       └── NO / 降级
    │               └── 规则引擎（classify_record + detect_symptoms + ...）
    │
    └── 统一输出结构：
        {pet_name, pet_id, record_type, severity, symptoms[],
         need_reminder, reminder{title, time}, reply, _parser}
```

**LLM Prompt 设计原则（parse_pet_record）：**

```
系统角色：宠物记录解析器，只输出 JSON，不输出 Markdown
输入上下文：已有宠物列表（用于消歧宠物名）+ 用户原始输入
输出约束：7 个必填字段，类型枚举严格限定
温度参数：0.1（追求确定性输出）
超时：15 秒
```

**规则引擎兜底逻辑：**

| 步骤 | 方法 | 说明 |
|------|------|------|
| 宠物识别 | `find_pet()` | 优先精确匹配宠物名，再模糊匹配，最后取第一只 |
| 类型分类 | `classify_record()` | 关键词规则，疫苗 > 驱虫 > 用药 > 健康 > 饮食 > 日常 |
| 症状提取 | `detect_symptoms()` | 8 种症状词典 |
| 严重度估计 | `estimate_severity()` | 高危词 → high；中等症状 → medium；其他 → low |
| 提醒判断 | `should_create_reminder()` | 触发词列表 + 记录类型策略 |
| 时间解析 | `resolve_reminder_time()` | 支持：一年后/下个月/下周/后天/明天/今晚/具体点钟 |

#### 3.2.3 前端架构

**单页应用（SPA），纯 Vanilla JS，无框架依赖：**

```
状态管理：全局 state 对象 {user, data, view, lastParsed, allLogs}
数据流：登录 → /api/state 全量拉取 → renderAll() 全量渲染
更新模式：任何写操作 → 服务端返回新 state → 覆盖本地 state → renderAll()
本地优化：健康日志筛选在客户端完成（避免重复请求）
持久化：localStorage 保存 user 对象，刷新自动恢复会话
```

### 3.3 关键流程：聊天记录一条完整链路

```
1. 用户输入 "小橘今天晚上吐了一次，明天早上提醒我观察"
        ↓
2. POST /api/chat {content: "..."}
        ↓
3. server.py: try_llm_parse() → （无 Key）→ 规则解析
        ↓
4. 解析结果:
   {pet_name:"小橘", pet_id:"pet-xiaoju",
    record_type:"health", severity:"medium",
    symptoms:["呕吐"], need_reminder:true,
    reminder:{title:"观察小橘呕吐情况", time:"明天早上",
              reminder_time:"2026-06-04T08:30:00"},
    reply:"已保存为小橘的健康日志，并生成提醒：观察小橘呕吐情况。"}
        ↓
5. INSERT INTO health_logs (...)
   INSERT INTO reminders (...)  ← reminder_time = 2026-06-04T08:30:00
        ↓
6. 返回 {parsed, state（完整新状态）}
        ↓
7. 前端：更新 state → renderAll() → 聊天流显示回复，首页提醒更新
```

### 5.2 LLM 与规则引擎对比效果

**规则引擎的局限性（发现的边界）：**
- `"小橘不太对劲，感觉很虚弱"` → 无法识别为健康异常（没有明确症状词）
- `"豆豆吃了点东西但没吃完"` → 归类为 diet 而非 health
- `"帮我记一下小橘今天去看了牙"` → 归类为 diary，无法识别为复诊

**LLM 的优势（接入后对比）：**
- 模糊语义理解：`"精神头不好"` 正确识别为 `symptoms: ["精神不佳"]`
- 隐式时间提取：`"明天下班后"` 正确解析为 18:00
- 多事件处理：`"小橘今早吃饭了，豆豆还有药没吃"` 可拆分为两条记录

**④ 迭代式完善**

随着使用深入，陆续提出以下完善需求，模型均能精确定位修改点：
- 添加 LLM 动态配置（UI 弹窗 + 后端端点）
- 添加宠物编辑/删除功能
- 添加提醒手动创建
- 添加语音输入

- 丰富演示种子数据

#### 6.1.2 运行时：LLM 作为 NLP 引擎

运行时 LLM 承担四类任务：

| 任务 | Prompt 策略 | 温度设置 | 说明 |
|------|------------|---------|------|
| 聊天记录解析 | 严格 JSON 输出约束，枚举字段类型 | 0.1 | 追求稳定确定性 |
| 养宠推荐 | 结构化 JSON，包含 score/reason/care_plan | 0.3 | 适当多样性 |
| 健康摘要 | 角色扮演（宠物健康助手），限制不做诊断 | 0.4 | 允许语言丰富性 |

**Prompt 工程关键设计：**

1. **角色定义明确化：** `"你是 PetCare Cloud 的宠物记录解析器"` 而非笼统的 `"你是助手"`
2. **输出格式强约束：** 明确指定 `"只输出 JSON，不输出 Markdown 代码块"`
3. **上下文注入：** 将用户已有宠物名列表作为上下文传入，辅助消歧
4. **后处理容错：** 服务端用正则剥离可能出现的 ` ```json ``` ` 包裹，再 JSON 解析
5. **失败降级：** 任何 LLM 调用失败（超时、格式错误、无 Key）均静默降级到规则引擎

| **多语言切换** | Python、JavaScript、CSS 无缝切换，风格一致 | ⭐⭐⭐⭐⭐ |
| **防御性编程** | 主动添加安全检查、错误处理、XSS 防护 | ⭐⭐⭐⭐⭐ |
| **中文 NLP**（规则+LLM）| 宠物名识别、症状提取、时间解析准确率高 | ⭐⭐⭐⭐ |
| **Bug 定位与修复** | 给出现象描述后能准确定位代码位置并修复 | ⭐⭐⭐⭐ |

#### 6.2.2 局限性与应对策略

| 局限性 | 表现 | 本项目应对策略 |
|--------|------|-------------|
| **幻觉 / 格式不稳定** | LLM 偶尔输出非 JSON 或字段缺失 | 后处理正则剥除 + 字段默认值兜底 + `normalize_parse()` 归一化 |
| **超时风险** | 网络不稳定时 LLM 调用可能超时 | 15 秒超时 + 静默降级规则引擎 |
| **无状态** | LLM 不记忆上下文，每次独立解析 | 每次调用都注入宠物列表上下文 |
| **成本** | API 调用有费用 | 可选配置，免费演示完全可用 |
| **代码幻觉** | 生成的代码有时引用不存在的变量 | 每次生成后运行测试验证 |

#### 6.2.3 开发效率分析

| 阶段 | 传统手写估计 | 模型辅助实际 | 提升倍数 |
|------|------------|-------------|---------|
| 后端路由 + 数据库（server.py）| ~8h | ~1h | 8× |
| 前端 SPA（app.js）| ~6h | ~0.5h | 12× |
| CSS 样式（styles.css）| ~4h | ~0.3h | 13× |
| Bug 修复与迭代 | ~3h | ~0.3h | 10× |
| **合计** | **~21h** | **~2.1h** | **~10×** |

> 说明：以上为估算。模型在**模板性较强、结构清晰的代码**（路由、CRUD、CSS）上提速最显著；在**业务逻辑细节**（时间解析边界、提醒触发规则）上需要人工测试验证。

#### 6.2.4 人机协作的最佳实践（经验总结）

1. **需求要具体，不要笼统。** `"帮我完善"` 效果不如 `"添加宠物删除功能，要求级联删除相关日志和提醒"`

2. **代码要跑测试，不要盲信。** 模型生成的时间解析逻辑存在"一年后"边界错误，只有通过测试脚本才发现

3. **分层迭代，不要一次全写。** 先让模型实现核心功能（聊天解析），验证后再扩展（LLM 配置、语音输入）

4. **提供上下文，不要孤立提问。** 每次修改时把相关函数的代码贴给模型，它的修复准确率明显高于只描述问题

5. **利用模型的防御性倾向。** 模型会主动加 `try/except`、路径检查、输入校验，不要删掉这些代码

## 七、项目总结

PetCare Cloud 验证了 **"LLM 作为 NLP 中台 + 规则引擎兜底"** 在垂直领域的可行性。核心价值：

- **降低记录门槛：** 自然语言输入替代表单填写，符合用户微信使用习惯
- **智能提醒生成：** 从对话中自动提取时间意图，减少遗漏
- **云原生架构：** SQLite → RDS、本地存储 → OBS、同步处理 → RocketMQ，每个组件均有云端替换路径

**关于 LLM 的核心结论：**

> LLM 在本项目中最大的价值不是"替代程序员"，而是**将非结构化的自然语言输入转化为结构化数据**这一传统 NLP 极难处理的任务上，以极低的工程成本实现了高质量的中文语义理解。在开发阶段，它将完整项目的工程成本压缩了约 10 倍，但**业务逻辑的正确性验证仍然必须依赖人工测试**。
